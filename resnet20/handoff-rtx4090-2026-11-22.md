# Handoff: rerunning the ResNet-20 study on another machine with an RTX 4090 (Nov 22, 2026)

How to set up a second machine with an RTX 4090 and run the Week 2 ResNet-20 bit-flip study again. Our official runs were done on the RTX 5090 PC at commit `27ee894`. Their results are in [`results-2026-11-20.md`](results-2026-11-20.md), and the method, step by step, is in section 2 of [`for-vgg-group-2026-11-21.md`](for-vgg-group-2026-11-21.md). This file covers only what is needed to run it again and check the result.

If an AI agent runs this, it should first read [`plan-resnet20-week2.md`](plan-resnet20-week2.md) and add a work-log row there after every step, as the repo's `CLAUDE.md` asks.

## 1. Two ways to rerun, and what each one tells you

| | A. Same trained models | B. From scratch |
|---|---|---|
| What runs on the 4090 | One-weight test, the 9,600-fault campaign twice, compare, summarize. It loads our saved models from `logs/fmnist_train/` and `logs/cifar10_train/`, which are committed in git. | Training as well, then everything in A on the new model |
| Question it answers | Does a different GPU give the same results for the same weights? | Do the conclusions hold for a freshly trained network? |
| What to expect | `chosen_elements.csv` is byte-identical to ours, because the weight choice uses only the seed and the network shape. `faults.csv` may differ slightly (see section 6). | Different weights, so every fault is different. Compare the totals and the per-bit, per-field and per-group tables, with their 95% intervals. |
| Time on our 5090, both datasets | about 20 min | about 32 min |

Do A first: it is quicker and has an exact reference. Then do B if you want it.

## 2. What the machine needs

- An NVIDIA RTX 4090 with a driver that supports **CUDA 13.4 or newer**. `nvidia-smi` shows the supported version in its top right corner. Our 5090 used driver 621.01.
- **Python 3.12.** We used 3.12.10. Newer versions may not have the pinned packages.
- **git**, and internet access for pip and the dataset download.
- Disk: about 0.5 GB for the datasets and a few GB for the virtual environment (PyTorch with CUDA is large).
- GPU memory: the largest step evaluates all 10,000 test images in one batch. On the 5090 that peaked at 3.1 GB (Fashion-MNIST) and 4.1 GB (CIFAR-10), so 24 GB is plenty.

**About the 4090 and this PyTorch build:** the pinned `torch 2.15.0+cu134` contains GPU code for `sm_75, sm_80, sm_86, sm_90, sm_100, sm_120`, but not the 4090's own `sm_89`. Code built for `sm_86` runs on `sm_89` (same major version), so it should work, and the smoke test in step 3.3 checks it. It also means the 4090 runs different GPU code from the 5090 (`sm_120`). That is one reason results may not be byte-identical across the two (section 6).

## 3. Setup

The commands are for Windows PowerShell, as on our PC. **On Linux**, use `python3.12` instead of `py -3.12`, `.venv/bin/python` instead of `.venv\Scripts\python.exe`, and forward slashes. The pinned `requirements.txt` was made on Windows and hasn't been tested on Linux. It should install there, since every pinned package has Linux builds.

### 3.1 Get the code

```
git clone -c core.autocrlf=false https://github.com/Tonylai2789/bitflip-diffusion.git
cd bitflip-diffusion\resnet20
git log --oneline -1
```

**Why `-c core.autocrlf=false`:** on Windows, git can convert line endings to CRLF on checkout. That changes the bytes of our `faults.csv` and `chosen_elements.csv`, and the cross-GPU `compare` in step 4.1 would report a false difference. The flag applies only to this clone. It isn't needed on Linux. To check after step 3.2 that our files arrived byte-exact (this should print `True` twice):

```
.venv\Scripts\python.exe -c "import json, hashlib; d = json.load(open('logs/compare_fmnist_campaign_a_vs_fmnist_campaign_b.json')); print(all(hashlib.sha256(open('logs/fmnist_campaign_a/' + f, 'rb').read()).hexdigest() == h[0] for f, h in d['sha256'].items())); d = json.load(open('logs/compare_cifar10_campaign_a_vs_cifar10_campaign_b.json')); print(all(hashlib.sha256(open('logs/cifar10_campaign_a/' + f, 'rb').read()).hexdigest() == h[0] for f, h in d['sha256'].items()))"
```

Use the latest `main`. It has the same code as `27ee894` (`src/resnet20_fault.py`, `src/bitflip.py`, `configs/resnet20.json` haven't changed since), plus our logs and the two trained models.

### 3.2 Create the environment

```
py -3.12 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt --extra-index-url https://download.pytorch.org/whl/cu134
```

### 3.3 Smoke test

```
.venv\Scripts\python.exe -c "import torch; print(torch.__version__, torch.cuda.is_available(), torch.cuda.get_device_name(0)); x = torch.randn(64, 3, 32, 32, device='cuda').half(); print(torch.nn.functional.conv2d(x, torch.randn(16, 3, 3, 3, device='cuda').half()).shape)"
```

It should print `2.15.0+cu134 True NVIDIA GeForce RTX 4090` and `torch.Size([64, 16, 30, 30])`. If it says `no kernel image is available`, the build doesn't run on this GPU. Stop and report it.

### 3.4 Unit tests

```
.venv\Scripts\python.exe -m pytest tests/ -v -rs
```

Every test must pass, and the CUDA cases must run, not be skipped. The first run downloads Fashion-MNIST and CIFAR-10 into `data/`, which git ignores.

## 4. Running it

**Rules:**

- **Run from `resnet20/`, on a clean committed tree.** Each `run.json` records the commit and whether tracked files had uncommitted changes (`git_dirty`). New log folders don't count as changes.
- **Use new run names.** Every run writes `logs/<run-name>/` and refuses to overwrite an existing folder. Our folders (`fmnist_*`, `cifar10_*`) are in the repo. The commands below use the prefix `rtx4090_`.
- The code's "CUDA is not available" error message mentions the RTX 5090. That's only wording: any CUDA GPU works.

### 4.1 Way A: same models (do this first)

Fashion-MNIST:

```
.venv\Scripts\python.exe src/resnet20_fault.py one-weight --model logs/fmnist_train/model_fp32.pt --run-name rtx4090_fmnist_one_weight
.venv\Scripts\python.exe src/resnet20_fault.py campaign --model logs/fmnist_train/model_fp32.pt --run-name rtx4090_fmnist_campaign_a
.venv\Scripts\python.exe src/resnet20_fault.py campaign --model logs/fmnist_train/model_fp32.pt --run-name rtx4090_fmnist_campaign_b
.venv\Scripts\python.exe src/resnet20_fault.py compare logs/rtx4090_fmnist_campaign_a logs/rtx4090_fmnist_campaign_b
.venv\Scripts\python.exe src/resnet20_fault.py summarize logs/rtx4090_fmnist_campaign_a
.venv\Scripts\python.exe src/resnet20_fault.py compare logs/fmnist_campaign_a logs/rtx4090_fmnist_campaign_a
```

CIFAR-10: the same six commands with `cifar10` in place of `fmnist`. For example, `--model logs/cifar10_train/model_fp32.pt --run-name rtx4090_cifar10_campaign_a`.

- The first `compare` checks that the 4090 repeats **itself**. It must print `"identical": true` and exit with 0.
- The last `compare` checks the 4090 against **our 5090 run**. It writes `logs/compare_fmnist_campaign_a_vs_rtx4090_fmnist_campaign_a.json`. If the files differ, it prints `"identical": false` and exits with 1. **That is a result, not a failure:** record it and go on to section 6.

The model's own `run.json` (in `logs/fmnist_train/`) provides the dataset name and normalization. Every run checks that the downloaded dataset files and the loaded weights match the hashes recorded there. If one doesn't match, the run stops.

### 4.2 Way B: from scratch

```
.venv\Scripts\python.exe src/resnet20_fault.py train --dataset fashion_mnist --run-name rtx4090_fmnist_train
```

Then the first five commands of 4.1, with `--model logs/rtx4090_fmnist_train/model_fp32.pt` and new run names, for example `rtx4090_fmnist_scratch_campaign_a`. Skip the last compare: the weights differ, so it would only report that the files differ. Do the same for CIFAR-10 with `--dataset cifar10`.

Training uses the same seed as ours, but GPU training isn't bit-for-bit repeatable, so the new model will differ slightly. Ours reached FP32 93.33% (Fashion-MNIST) and 91.38% (CIFAR-10). Expect values close to those, not equal.

## 5. Checks: what must pass, and what a failure means

The code stops by itself if any of checks 1–4 fail.

| # | Check | Where to see it | If it fails |
|---|---|---|---|
| 1 | FP16 accuracy within 0.1 pp of FP32 | `run.json`: `fp16_fp32_diff_pp` | Stops. Report the two accuracies. |
| 2 | Fault-free FP16 network gives identical logits twice | `run.json`: `double_eval_identical` | Stops. The GPU setup isn't deterministic. |
| 3 | Sanity fault (bit 14 of the largest `fc` weight below 1) changes the outputs, and restoring brings back the exact reference | `run.json`: `sanity_check` | Stops |
| 4 | After every fault, the weight tensor's SHA-256 equals its value before the flip | checked inside the run | Stops. Restore failed. |
| 5 | `campaign_a` and `campaign_b` on the 4090 are byte-identical | first `compare` | Not repeatable on this GPU. Report it, and don't use the results. |
| 6 | Way A only: same `chosen_elements.csv` as ours | last `compare`, the `chosen_elements.csv` hashes | Should never differ. If it does, the seed handling or the code differs: stop and check the commit. |

**Our numbers to compare with (Way A):**

| | Fashion-MNIST | CIFAR-10 |
|---|---|---|
| FP32 / FP16 accuracy (evaluation) | 93.33% / 93.32% | 91.38% / 91.35% |
| `reference_logits_sha256` (first 8 characters) | `16642a00` | `e923c063` |
| Masked / SDC / non-finite | 5,017 / 4,525 / 58 | 3,300 / 6,172 / 128 |
| One-weight test | `layer3.1.conv1.weight[29070]` = 0.060333251953125, bit 14 → 3954.0 | `layer3.1.conv1.weight[28942]` = −0.1248779296875, bit 14 → −8184.0 |
| Campaign time on the 5090 | 4.2 min each | 5.3 min each |
| Training time on the 5090 (Way B) | 6.2 min | 5.9 min |

The one-weight row must match exactly, because it depends only on the seed and the weights. Its accuracy column may differ like the campaign's.

## 6. If the 4090 doesn't match the 5090 exactly

This is possible, and it's worth recording. Same weights and same seed, but:

- the two GPUs run different compiled code (`sm_86` on the 4090, `sm_120` on the 5090);
- even in deterministic mode, cuDNN can choose different convolution algorithms on different GPUs;
- FP16 adds numbers in whatever order the algorithm uses, so the last bit of a logit can differ.

Our test sets have a few images whose top two scores are almost tied: 26 (Fashion-MNIST) and 34 (CIFAR-10) have a gap below 0.1 (results write-up, section 6). A last-bit difference can flip one of them, and one flipped image turns a masked fault into SDC.

What to look at, in this order:

1. **`reference_logits_sha256`** in `rtx4090_*_campaign_a/run.json` against ours above. If it differs, the fault-free reference already differs, so `faults.csv` almost certainly will too.
2. **The FP16 accuracy** against ours. If it's equal, the reference predictions are probably the same, and only the logits differ.
3. **`class_totals`** in `run.json`, and `per_bit.csv`, `per_field.csv`, `per_group.csv`, against ours. If the shares fall inside each other's 95% intervals, the conclusions are unchanged.
4. **How many faults changed class.** Join the two `faults.csv` files on (`tensor`, `element_index`, `bit`) and count rows whose `class` differs. We expect any differences to be masked ↔ SDC at low bits.

## 7. Afterwards

- Add a work-log row to `plan-resnet20-week2.md` for each step, with the commit and the main numbers, as the existing rows do.
- **What to commit:** the same set as our official runs: each run's `run.json`, CSVs, `per_bit.png`, the compare JSONs, and for Way B the new `model_fp32.pt`. PNG, `.npy` and `.pt` files are ignored by `.gitignore`, so add them with `git add -f`. Never commit `data/` or `.venv/`.

It requires the logits to match our 5090 reference exactly, so on the 4090 it may stop with a hash mismatch. That only tells you what check 1 in section 6 already shows.
